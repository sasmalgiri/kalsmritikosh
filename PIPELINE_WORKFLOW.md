## E. FINDINGS — correctness, with the failure story

### F-1 · HIGH · Swallowed entity-insert error cascades into wrong events
`IngestCoordinator.swift:1520`
```swift
canonicalMapping = (try? await entities.insertBatch(raw)) ?? [:]
```
If the insert throws, `canonicalMapping` becomes **empty** — and 24 lines later
`events.insertBatch(remapped)` (`:1544`) writes events remapped through that
empty mapping. So a single swallowed DB error does not merely lose entities: it
persists events whose entity references were never canonicalised. The ledger ends
up internally inconsistent, and nothing records that it happened.

### F-2 · HIGH · `history_chapters` is written and never read
`HistoryArtifactRepository.swift:77` inserts chapters on every history build.
That same repository selects `history_items`, `history_artifacts`,
`history_gaps`, `history_item_evidence` — and never `history_chapters`.
Compounding it: the test named *"Save persists the full graph and reloads"*
asserts header, coverage, `itemCount`, `gapCount`, `evidenceCount` and review
status. There is no chapter assertion and no `chapterCount` helper. A write-only
table inside a passing suite whose name claims completeness.

### F-3 · HIGH · Two FTS indexes are never populated
`qa_pairs_fts` and `synthetic_questions_fts` have **no producer**
(`PIPELINE_MATRIX.md`). So question-side search has an index and no contents —
any query against them silently returns nothing.

### F-4 · MED · Recursive member ingest swallows failures
`:1042`, `:1067`, `:1123` — `let r = try? await self.runIngest(...)`. A ZIP
member, an iOS-backup file or an email attachment that fails to ingest yields
`nil`, is recorded as `childSourceVersionID: nil`, and the reason is lost. For a
forensic tool this is the worst place to lose a reason: the examiner cannot tell
"not in the container" from "failed to parse".

### F-5 · MED · `linkBlocks` failure breaks the claim–evidence contract silently
`:1146` — `try? await evidenceStore.linkBlocks(...)`. If this fails, blocks are
never linked to their KO, so facts derived from those blocks cite evidence that
cannot resolve. The claim–evidence contract is the product's core promise, and
this is the one call that wires it.

### F-6 · MED · Embedding upsert failures are indistinguishable from "pending"
`:372`, `:398` — `try? await vectors.upsert(...)`. A failed embedding leaves the
chunk simply absent from `chunk_embeddings`, which reads identically to
not-yet-drained. Coverage can never be honest about *failed* vs *pending*.

### F-7 · MED · `knowledge_objects_fts` is maintained and never queried
Triggers keep it in sync on every `knowledge_objects` write
(`SchemaMigrations:1226–1234`) and nothing selects from it. Either dead cost on
the hot ingest path, or a retrieval lane that was designed and never connected.

### F-8 · LOW · An eighth retrieval layer exists that the invariant does not name
`bondLayer` (`HybridRetriever:918`) sits between Graph and Vector. CLAUDE.md's
documented priority lists seven. The code is reasonable; the doc is what
reviewers check against.

### F-9 · LOW · `boilerplate_uses` written, never consulted
`BoilerplateRegistry:92`. Boilerplate associations cannot influence any
behaviour.

### F-10 · LOW · Nine tables with no producer
`companies`, `people`, `projects`, `timelines`, `evidence_block_edges`,
`history_alternative_accounts`, `qa_pairs_fts`, `synthetic_questions_fts`,
`vectors`. `vectors` is deliberate (a migration reads it to backfill
`chunk_embeddings`). `history_alternative_accounts` has a test suite and no
writer. The rest need a verdict.

### Not yet established (UNKNOWN — stated rather than assumed)
- `narrativeSlotExtractor` (`:1576`) — what it writes and whether anything reads it.
- Transaction boundaries across B2–B8: is one KO's derivation atomic, or can a

- Whether any retrieval query is unbounded (no LIMIT) on a large ledger.
- `document_profiles`, `derived_objects`, `enrichment_status`, `event_versions`
