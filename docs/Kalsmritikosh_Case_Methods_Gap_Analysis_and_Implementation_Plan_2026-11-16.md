## B. How the 16 existing methods contribute

The proposed review records one outcome for each registered method version: **useful now, already covered, needs an input, useful later, or inapplicable**, each with its reason. Interrupted or unavailable assessments are **not assessed**. A run cannot silently omit a method. Deterministic guidance remains available offline. AI may propose additional reasons and checks under the case's permission. Neither mode marks a method complete. When a person elects to perform it, open or create its actual method run through the existing lifecycle.

| Existing method | Question it contributes | Example output to retain on the case |
|---|---|---|
| Brainstorming | Which materially different explanations have we overlooked? | Unreviewed idea, proposed discriminating observation |
| 5W1H | Which who, what, when, where, why or how is unknown? | Missing attribute, relevant source and request |
| Hypothesis matrix | Which evidence counts against each explanation? | Competing hypotheses and an unassessed cell where appropriate |
| Evidence collection plan | What should we obtain, from whom, and by when? | Itemized request with custodian, expiry and expected result |
| Five Whys | What upstream condition might explain this observation? | Branching Why links; source, assumption or evidence gap at each step |
| Fishbone / Ishikawa | Which families of causes have received little scrutiny? | Candidate cause under a configurable branch and a test |
| Root-cause assessment | Which causal account survives the alternatives? | Reviewed causal assessment or an explicit inconclusive result |
| Corrective and preventive action | What change addresses the established cause or failed safeguard? | Owner and action tied to a reviewed basis; defer if premature |
| Effectiveness review | Did the corrective action change the outcome? | Follow-up measure, observation window and review date |
| Contradiction matrix | Are two statements genuinely about the same event and subject? | Both exact passages, contexts and possible reconciliation |
| Gap analysis | What expected evidence is absent within the checked scope? | Missing item, search coverage and residual uncertainty |
| Timeline analysis | What sequence is possible once uncertainty is included? | Event time, observation time and reporting time with precision |
| Relationship analysis | Which direct or indirect link matters, and what supports it? | Typed link, source and independence status |
| Transaction flow | Where did the value go, and what was reversed or duplicated? | Sourced entries and reconciliation per account and currency |
| Risk matrix | Which plausible consequence or expiring source needs attention? | Rationale and urgency beside uncertainty; no implied guilt |
| Decision matrix | Which next checks best distinguish the remaining explanations? | Compared options with costs, expected outcomes and override reason |

Screen the registry without requiring 16 paid calls. A bounded structured pass or small batches can propose ideas. The app verifies coverage of method IDs, source references and actual tool results. Display the best few distinct checks plus a visible **Show all**, including minority branches, deferred methods and missing inputs. Reaching a budget must leave a visible continuation.

## C. Minimal data contract

Use the encrypted case ledger, case identity and revision guards. The names below describe logical records, not a mandate for new tables. First map them to existing method runs, tasks, AI proposals, evidence requests, query receipts and change dependencies. Add only relationships or fields that are missing.

| Record | Minimum information |
|---|---|
| Case review | Case and optional focus-node ID; question; scope and access revision; method catalog version; actor; time; mode; run state; input versions; actual model/provider where applicable; coverage receipt |
| Method assessment | Review ID; method ID/version; applicability and reason; referenced prior run; proposed path IDs; failure or unassessed reason |
| Line of inquiry | Stable ID; neutral explanation; supporting, contrary and dependent sources; assumptions; predictions; discriminator; originating methods; status and decision history |
| Evidence check | What to inspect; expected observations under each alternative; evidence custodian; preservation deadline and its source; cost/effort if known; local query/request/action IDs; ambiguity and outcome |
| Coverage receipt | Eligible versioned records, access-safe counts, unreadable/unindexed records, records and passages actually examined, subject/batch boundaries, remaining work, cursor and termination reason |
| Return and handover | Case/action/request item, accepted source version, locators, attribution, reviewer, prior decision, revision dependency and reopened/unchanged outputs |

Reuse one canonical record across branch appearances. Multiple methods can propose the same check. Suggest a merge only when target identity, relevant time, requested evidence and expected observations are compatible. Keep a reversible merge decision. Different desired observations may share one request while retaining distinct hypotheses. Record an invariant-based retry key for review creation and accepted actions. Recheck case state, permissions, model destination and input versions before a send, at apply, and before export using existing guards. Stop late writes to closed or erased cases. A restored case preserves review history without restoring obsolete send permissions or replaying external requests.

## E. Decisive fixture to build first

**Scenario:** a failed pharmaceutical-quality batch initially attributed to a supplier. The packet includes two apparent lab confirmations derived from the same raw run, a namesake instrument, a plausible material explanation, a sample accession discrepancy, a permitted calibration record beyond the first 400 documents and a time-limited raw log. Give the preservation deadline a source. Include a withheld item and one unreadable record. This is a designed engineering fixture, not a completed investigation.

1. With no contradiction selected and AI off, start the review from the failed-test point. Check all 16 applicability outcomes. Identify that the two confirmations might share an origin. Preserve the uncertainty when their independence cannot be established.
2. Distinguish supplier variation, instrument drift, sample identity and dependent confirmations. Require one observation that could separate the first two hypotheses. The app should surface the expiring log with its rationale. A duplicate suggestion from another method must not produce another request.
3. Search with coverage, continue beyond the old cap, open the correct instrument record, and show why the namesake is excluded. Test a version in which the decisive record is genuinely unavailable; the expected conclusion changes to an open question.
4. Approve a narrowly scoped specialist request, first by manual follow-up and then through any supported adapter. Admit a partial answer. Inject a later correction as legitimate returned evidence. Check precisely what is stale and who must review it.
5. Hand over an inconclusive or supported brief, as appropriate to the fixture variant. A second reviewer must reach every cited passage and see what was still unverified at the time. Record the initial and amended handovers.
