## 1. What is protected

| Asset | Where it lives |
|---|---|
| Originals: the person's files | In place (bookmarks). Copies are kept in the evidence vault by default (sealed, IN-02; a person may turn it off), and exist in complete backups, snapshots and intake. |
| Derived ledger: text, facts, entities, events, studio work, case history, job results, releases, send log | SQLCipher database (AES-256); key in the Keychain (this device only) |
| Indexes and caches | FTS inside the ledger; vector cache `hnsw-index.bin` beside it, **sealed with AES-GCM under a key derived from the ledger key** (K11; never written without the key; an unsealed or foreign cache is rebuilt, not trusted) |
| Work products: exports, receipts, bundles | Wherever the person saves them (plaintext by design, recorded with their digests) |
| Secrets | Ledger key, Online API keys, signing keys (Keychain, this device only); recovery key (shown once) |
| Purchase state | Verified StoreKit transactions (Apple); the app caches only the last verified entitlement, never an unlimited one |

## 2. Who might attack, and how

| Actor | Capability | Main concern |
|---|---|---|
| Someone with the unlocked Mac, or a backup disk | Reads files in the container, backup folders and Downloads | Opened (plaintext) copies while the app runs, vault copies stored by builds before IN-02, originals in complete backups and snapshots, intake, notes, AI outputs and exports (see docs/STORAGE_KEY_INVENTORY.md) |
| Another process run by the same user | Reads non-sandboxed locations, the pasteboard and the unified log | Clipboard, logs, temp files |
| A malicious document in the archive | Its text reaches the rules, the on-device model and (Online) the cloud AI | Prompt injection; parser exploits |
| The chosen AI provider, or a provider-side breach | Receives what Online sends | Retention; use beyond the request |
| A network attacker | Sees the helper's HTTPS traffic | Downgrade or redirect to other hosts |
| The person themself, by mistake | Approves a send, exports, erases | Sending the wrong material; irreversible actions |
| A billing failure or a store outage | Changes the entitlement | Work locked away or deleted by a billing state (never); unlimited access from an unverified state (never) |

## 2a. Actors added in version 4 (S9)

| Actor | Capability today | Control | Bounded conclusion |
|---|---|---|---|
| Another person named in a case role (investigator, reviewer, contributor, viewer) | A name recorded on this Mac — **not an account**. Everyone using this macOS account can act as this Mac's owner | Per-case roles enforced in the services (T17); every change in a team case must be recorded under a name holding a role that allows it | Locally enforced, **not authenticated**: anyone at the keyboard can type another name. Binding names to real identities needs ARCH-08 (planned: Apple CloudKit sharing, after a solo release) |
| An external contributor | Nothing in this version: there is no submission channel (TEAM-03) | The contributor role reads only the requests shared with it and never the case list, titles or counts | No portal or upload service exists; a contributor cannot reach the app except at this Mac |
| A remote team service / shared store | **Not built** (scope decision: CloudKit sharing after a solo release) | — | When built: transport and at-rest encryption, who can decrypt, revocation and key rotation must be designed and this model revised (SEC-04) |
| The folder-sync store (one person's devices) | Any device registered in the store can write a signed batch of the user layer (tags, groups, notes, highlights, case issues) | AES-GCM under a passphrase key; signed batches; quarantine; **rows an erasure removed are never re-created by a batch** (T19) | `store.json` and device names are plaintext (L8); a passphrase holder can still add new rows |
| The portable (companion) viewer | Opens a snapshot the person exported | Snapshot verification (`SnapshotVerifier`); re-encrypted with an export passphrase | Originals and manifest names inside the snapshot are plaintext (L7) |
| An administrator of this Mac or of a future shared service | Reads every file of the user account; on a service, operates the servers | FileVault (Mac), SQLCipher ledger; no service exists | A Mac administrator with the user's login can read the ledger through the app. Server-side administrators: undefined until a service exists — server-side processing must not be described as end-to-end encryption |

## 4. Supported workload

Measured (`docs/SUPPORT_ENVELOPE.md`, Mac16,12, 16 GB, macOS 27.0.1): 400 and 4,000 generated text documents ingest at
25.1 and 22.7 documents/s; peak memory +294 and +347 MiB; answers p95 1.9 and 2.5 s. Bounded-memory streaming of a
50,000-message mbox and a 300,000-row SQLite database (`ScaleRunTests`). Not claimed: very large or scan-heavy archives,
other hardware. Re-measure on the final implementation before stating figures in the listing.

## 6a. Key handling (S9)

- The ledger key, Online API keys, sync and signing keys live in the Keychain of this Mac only; the test host uses its own item and an in-memory store. None is written to the ledger, the preferences, an export, a backup manifest, a log line or a diagnostics file (each case's AI permission in the preferences holds, with your own key, a 16-character salted one-way fingerprint of it, so a replaced key asks again; the key cannot be recovered from it); credential-shaped text pasted into a case is masked in exports and the action log (T20).
- The vector cache, evidence vault and backup-manifest keys are derived from the ledger key (HKDF; purposes `hnsw-cache`, `evidence-vault`, `backup-manifest`) and never stored. The sync store key comes from the person's passphrase; losing it loses the sync store, never the ledger.
- Erasure does not remove Keychain items (disclosed, T10). The recovery key is shown once and copied concealed.
- A future team service (CloudKit) must define per-recipient keys, rotation and revocation before any shared case content is stored (SEC-04); until then no case record leaves this Mac through sync.
- Investigated: `ManagedFileProtectionTests.sealedCache` failed twice in the long S8 batches and passes alone. The cache is written with `NSFileProtectionComplete`, which refuses writes and reads while the Mac is locked; the batches ran for hours. The test now names the failing step and the system error so a lock is told apart from a defect. Consequence in the app: with the Mac locked, the cache is not saved and is rebuilt from the ledger at next use (never read unsealed).
